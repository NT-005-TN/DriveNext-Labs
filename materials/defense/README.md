## Подготовка к показу

- Сначала отрепетировать нужную лабу на том же устройстве. Сборка и автотесты не доказывают полный успешный вход Google, доставку письма и все действия после входа.
- Для лаб 2–5 подготовить собственный учебный аккаунт с доступной почтой, интернет и настроенный Google provider. Для лабы 4 заполнить имя, фамилию и номер удостоверения из 10 символов.
- Использовать только вымышленную анкету. Картинки: [машина](../demo_photos/test_car.png) и [тетрадь вместо документа](../demo_photos/test_notebook.png). Их надо заранее перенести в фото/файлы эмулятора. Для лабы 2 используется системный Photo Picker, для фото машины — выбор документов.
- В Supabase при показе фильтровать таблицы по своему тестовому UUID. Не показывать токены, пароли, Google client secret и чужие анкеты.
- Не запускать SQL-миграции во время защиты: это код настройки уже созданной базы, а не команда для каждого запуска приложения.
- Не очищать данные всех приложений. Сброс для повторного онбординга нужен только отдельной учебной копии ЛР1; он удалит её локальные настройки.

| Автомобили | Table Editor → cars | Своя машина, active, photo_paths |
| Фото машины | Storage → car-photos | Папка владельца и автомобиля |
| Бронь | Table Editor → bookings | Свои даты, start_time, total и status |
| Онбординг | Локальные SharedPreferences | Повторный запуск без вводных страниц |
| Избранное | Локальная Room | Database Inspector → favorite_cars при запущенном приложении |

Лабы 2–5 используют один сервер, но разные локальные данные и адреса возврата. Созданная на сервере машина видна и в других лабах с каталогом. Избранное между приложениями не синхронизируется.

## Короткие ответы на общие вопросы

**Activity и Fragment.** Activity — компонент экрана, объявленный в манифесте. Fragment — часть интерфейса со своим жизненным циклом, размещаемая внутри Activity. В ЛР1 один класс фрагмента показывает разные вводные страницы.

**Binding.** XML не превращается в Activity. При сборке ViewBinding генерирует класс со ссылками на View с идентификаторами. `inflate(layoutInflater)` создаёт дерево View по XML; `layoutInflater` — объект, который умеет читать разметку. `binding.root` — корень этого дерева, `setContentView(binding.root)` показывает его. Через `binding.title.text` меняем текст конкретного элемента, через `setOnClickListener` назначаем действие.

**Жизненный цикл Activity.** `onCreate` создаёт интерфейс → `onStart` экран становится видимым → `onResume` с ним можно взаимодействовать → `onPause` теряет фокус → `onStop` скрыт → `onDestroy` уничтожается. При возвращении из остановленного состояния: `onRestart → onStart → onResume`. При уничтожении процесса вызов onDestroy не гарантирован. Поэтому важные данные сохраняются заранее, а не только там.

**ViewModel.** Хранит состояние и выполняет работу, не привязываясь к экземплярам кнопок. Переживает обычное пересоздание Activity, но сама по себе не сохраняет данные после уничтожения процесса. Для этого нужны сохранённое состояние, локальное хранилище или сервер.

**Intent.** `Intent(this, Screen::class.java)`: this — контекст текущего экрана, второй аргумент — класс назначения. `putExtra("id", car.id)` переносит идентификатор выбранной записи; другой экран читает его и загружает данные. Это не передача всей базы.

**Корутина.** `viewModelScope.launch` запускает работу, связанную с ViewModel. `withContext(Dispatchers.IO)` переносит блокирующую работу с сетью/диском с UI-потока. `suspend` разрешает приостановку функции, но само по себе не означает отдельный поток.

**SharedPreferences и Room.** SharedPreferences — локальные пары ключ–значение, не кэш. Room — слой над SQLite для таблиц и запросов. Очистка данных приложения удаляет оба локальных хранилища, но не серверный аккаунт Supabase. После очистки можно войти в существующий аккаунт, а не обязательно регистрироваться заново.

**RLS и ключ.** Publishable key идентифицирует клиентский доступ к проекту и не является паролем администратора. JWT сессии сообщает, кто вошёл, а RLS ограничивает доступ к строкам на сервере. Скрыть кнопку в приложении недостаточно для защиты базы.

## Границы демонстрации

В ЛР1 LoginActivity — намеренная заглушка; настоящую авторизацию показывать в ЛР2. В ЛР2 главный экран подтверждает сессию, но ещё не является каталогом. В ЛР3–5 общий набор экранов шире темы отдельной лабы: защищать прежде всего её основной сценарий.

Переключатель уведомлений сохраняет настройку, но не подключает push-сервис. Адрес машины вводится текстом, без карты и геокодирования. Расчёт аренды не списывает деньги. Старые видео и Word из materials/archive описывают предыдущую реализацию и для текущей защиты не подходят.
